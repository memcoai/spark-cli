## Agent Rules

Always use Spark MCP tools to query shared memory **before** coding. Spark MCP provides software development guidance, including internal policies and best practice used in my team, information about proprietary code, and shared problem-solving knowledge from my software development team.

1. Call `mcp__spark__search` with tags describing your context to search existing knowledge.
2. If you discover anything new, call `mcp__spark__enrich_memory` to share it with the rest of the team.
3. **Always** call `mcp__spark__share_feedback` before finishing if you received any information from Spark.

## Project Overview

Node.js CLI tool (`@memco/spark`) that provides a command-line interface to the Spark knowledge network — a collective memory system for AI coding agents. ES modules throughout (`"type": "module"`), requires Node >= 20.17.

The CLI is itself an **MCP client**: the knowledge-network commands (`search`, `enrich_memory`, `create_memory`, `share_feedback`, …) are no longer hand-rolled REST calls — they are derived dynamically from the hosted MCP server's `tools/list` (registered under the verbatim server tool name, with all inputs as schema-derived flags) and executed over Streamable HTTP via `@modelcontextprotocol/sdk` against `${getApiBase()}/mcp`. Lifecycle/auth/maintenance commands stay static and hand-written. See "MCP command surface" under Key Patterns.

## Getting Started

Spark installs as a plugin from the MemCo marketplace (`memcoai/marketplace`) for Claude Code, Codex, and Cursor, backed by the `spark` CLI.

1. **Install the CLI:** `npm install -g @memco/spark`
2. **Login:** `spark login` (opens browser for OAuth authentication)
3. **Init:** `spark init` (interactive IDE setup wizard — adds the marketplace, detects the variant (public/teams), and installs the matching plugin + skills for Claude Code, Cursor, Windsurf, etc.)
4. **Verify:** `spark status` (checks version, auth, and skills status)

**Manual plugin install:** Claude Code — `/plugin marketplace add memcoai/marketplace` then `/plugin install spark-cli@MemCo` (teams: `spark-team-cli@MemCo`). Codex — `codex plugin marketplace add memcoai/marketplace` then `codex plugin add spark-cli@MemCo`. Cursor — Dashboard → Settings → Plugins → Add Marketplace → Import from Repo → `memcoai/marketplace`. The marketplace also hosts the MCP variants `spark-mcp` / `spark-team-mcp`.

**Updating:** `spark update` updates both the CLI and skills for all configured IDEs.

## Key Patterns

- **Zod validation:** Zod (`src/schemas.js`) validates everything EXCEPT live tool arguments: CLI inputs (tags, feedback entries), OAuth responses (token exchange, discovery metadata), API responses, settings.json reads (incl. the `toolManifest` cache via `toolManifestCacheSchema`), and version check responses. Use `z.looseObject(...)` on API/external response schemas to tolerate extra fields. Use `.safeParse()` with fail-open semantics for non-critical paths (version checks, settings reads). Use `.parse()` for critical paths (token exchange, API calls). When adding new schemas, preserve existing error messages by using `ctx.addIssue()` in `.transform()`. Live tool-argument validation does NOT use Zod — it runs the args against the server's JSON-Schema `inputSchema` via the SDK's bundled ajv (see "Server-as-source-of-truth validation").
- **MCP command surface (hybrid):** The CLI has two kinds of commands. (1) **Static lifecycle commands** (`login`, `logout`, `whoami`, `update`, `init`, `enable`, `disable`, `status`, `uninstall`) are hand-written in `bin/spark.js` and unchanged. (2) **Dynamic tool commands** are a PURE reflection of the MCP server: each is registered under the **verbatim server tool name** (e.g. `search`, `enrich_memory`, `create_memory`, `share_feedback`, and any future server tool — no friendly-name remapping, no kebab-casing of the command) with **all inputs exposed as schema-derived flags** (no positional arguments). They are generated at startup from the cached MCP `tools/list` manifest: `bin/spark.js` calls `registerToolCommands(program, getManifestForRegistration())` after the static commands and before `program.parse()`. Registration is synchronous and offline (reads the cache, zero network on the `--help`/`--version`/static path). An empty or foreign-apiBase cache registers no dynamic commands and adds a "run `spark login`/`spark init` to load available commands" help hint. Adding/changing a server tool requires no CLI code change — it appears under its server name after the next `spark login`/`spark init` or TTL refresh.
- **Server-as-source-of-truth validation:** The server's `tools/list` `description` + `inputSchema` (JSON Schema) are the single runtime authority for tool descriptions, flags, and argument validation — there is no Go schema export or codegen. `tool-commands.js` derives commander flags from each tool's `inputSchema` (`deriveFlags`), and the generic action validates the assembled args against the live schema via the SDK's bundled ajv (`validateArgs` in `mcp-client.js`) BEFORE any network call — an invalid arg produces a friendly error and exit 1 without ever reaching `tools/call`. Client-side validation is for nice error messages only; the server stays authoritative (the SDK's `callTool` validates output, not input, so this client input check is needed). Unsupported `inputSchema` shapes (nested object, array-of-non-string) fail loudly at registration time rather than silently dropping args.
- **Tool manifest cache:** A 24h-TTL snapshot of the server's `tools/list` lives in `settings.json` under the `toolManifest` key (`{ tools, checkedAt, apiBase }`, validated by `toolManifestCacheSchema`, fail-open). Each tool entry carries `serverName` (the verbatim `tools/list`/`tools/call` name — the single field used for both registration and the call; there is no friendly `name` field and no remapping), `description`, `inputSchema`, optional `outputSchema`. The cache is populated eagerly on `spark login` and `spark init` (fail-open, never aborts the command) and refreshed lazily on a tool call when stale (TTL elapsed or `apiBase` changed); it is keyed by `apiBase` so switching base never serves a foreign manifest. Unlike the global-only version caches, it is written to the **active settings path** (local-first via `getActiveSettingsPath`, matching credentials resolution) so a `spark login --local` manifest is found. `getManifestForRegistration()` reads it synchronously/offline and returns `[]` for an empty or foreign-apiBase cache (no stale foreign command surface).
- **MCP auth (SDK-driven OAuth):** The MCP transport's auth is decided by `getAuthMode()`. **OAuth mode** attaches a `SparkOAuthProvider` (an MCP SDK `OAuthClientProvider`) as the transport's `authProvider`: the SDK sources the Bearer from `provider.tokens()`, and on a 401 it auto-refreshes-and-replays by calling `auth(provider, …)` with the stored refresh token — there is NO CLI-side retry, no `is401`/`StreamableHTTPError` handling. NO static `Authorization` header is set in OAuth mode (the provider supplies the token). **API-key mode** (`--api-key`/`SPARK_API_KEY`/legacy stored key) sends a static `Authorization: Bearer <token>` via `requestInit.headers` and attaches NO provider, so the SDK's 401-refresh branches are dead and a 401 propagates unretried. (Backend `aud` landmine: a persistent 401 may be the backend token-claim issue, not a CLI bug — do not special-case it in CLI code.)
- **Avoid code duplication:** Extract shared logic into reusable helpers rather than duplicating code across commands. For example, `enable.js` and `disable.js` reuse helpers exported from `init.js` and `uninstall.js` respectively. When adding new commands or features, check for existing utilities before writing new code.
- **Settings file:** All persistent state stored in `settings.json` with structure `{ apiBase, credentials, clients, latestVersion, compatibility, skillsVersion, toolManifest, projects, globalInit }`. Global at `~/.spark/settings.json`, local at `./.spark/settings.json`. Credentials, client data, and the tool manifest use `readSettingsKey`/`writeSettingsKey` from `settings.js`.
- **API base URL:** Resolved via `getApiBase()` from `constants.js`. Priority: `SPARK_API_BASE` env var > local `apiBase` setting > global `apiBase` setting > `DEFAULT_API_BASE` (`https://spark.memco.ai`). Can be set via `spark login --api-base <url>` (persists to settings.json; `--local` controls which file). This is a developer-only feature. Trailing-slash stripping is centralized in `normalizeApiBase(base)` (`constants.js`) — used by `api.js`, `credentials.js`, `oauth.js`, `mcp-client.js`, and `validateApiBase`; it strips a trailing slash run (`/\/+$/`) without trimming or validating (distinct from `validateApiBase`, which trims + validates + returns `undefined` on malformed input).
- **Per-URL credentials:** Credentials are stored keyed by API base URL: `{ credentials: { "https://spark.memco.ai": { accessToken, ... } } }`. Old flat credentials are lazily migrated to per-URL format under `DEFAULT_API_BASE`. All credential functions accept an optional `apiBase` parameter, defaulting to `getApiBase()`.
- **Per-URL OAuth clients:** Dynamically-registered OAuth clients are stored per URL under the `clients` key: `{ clients: { "https://spark.memco.ai": { client_id, ... } } }`. Old flat `client` key is migrated to `clients[DEFAULT_API_BASE]`. This map IS the provider's `clientInformation()`/`saveClientInformation()` storage — the SDK performs dynamic client registration during `auth()` and the provider persists the result here (`loadClient`/`saveClient` in `oauth.js`). `SPARK_CLIENT_ID` env var overrides the stored client. There is no longer a per-URL OAuth-metadata cache — discovery is re-run by the SDK each `auth()`.
- **Credentials resolution:** local-first (`./.spark/settings.json`) then global (`~/.spark/settings.json`). The `--local` flag on `spark login` scopes credentials to the current directory. Token refresh auto-detects which location to save back to. Logout removes the credentials for the active API base URL, not the file. The local-first vs global _write_-location decision is centralized in `resolveActiveSettingsPath({ local, exists })` (`credentials.js`): consumed by `saveCredentials` (honoring its explicit `--local` override) and by `tool-manifest.js`'s `getActiveSettingsPath` (so the manifest lands next to the credentials). The injectable `exists` keys on settings-FILE existence.
- **Auth priority:** CLI `--api-key` flag > `SPARK_API_KEY` env var > stored legacy API key (`apiKey`/`token`) > OAuth access token. `getAuthToken()` resolves the token string in that order (or `null`); `getAuthMode()` returns `'apikey'`/`'oauth'`/`null` from the same precedence. The `--api-key`/`SPARK_API_KEY` path attaches NO OAuth provider anywhere (transport or `getCurrentUser`) and is never refreshed.
- **Login flow (SDK orchestrated):** `spark login`'s `runOAuthFlow` drives the MCP SDK `auth()` orchestrator against a `SparkOAuthProvider`, in exactly two calls: the first `auth(provider, { serverUrl: \`${apiBase}/mcp\` })`runs discovery + dynamic client registration + PKCE, builds the authorize URL, and hands it to the provider's`redirectToAuthorization`(which appends`provider=authkit`and opens the browser), returning`'REDIRECT'`; the CLI's own loopback callback server captures `?code=`(validating the provider's`state()`); the second `auth(provider, { serverUrl, authorizationCode })`exchanges the code and the provider's`saveTokens`persists credentials. There is no hand-rolled PKCE/exchange and no manual`saveCredentials`in`loginCommand`. The loopback server, browser-open, redirect URLs, and 5-min timeout are unchanged. `checkExistingAuth`reuses the provider +`auth()`for a browserless refresh-token grant when the stored token is expired (gated by`isTokenExpired`).
- **Token refresh (SDK-driven):** Refresh is fully reactive and owned by the SDK `auth()` orchestrator. For MCP tool calls the transport's `authProvider` auto-refreshes-and-replays on 401; for the REST `getCurrentUser`, a 401 in OAuth mode triggers one `auth(provider, …)` refresh + a single retry. In both cases the provider's `saveTokens` writes the new token back to the same settings.json the credentials came from. There is NO proactive refresh in `getAuthToken()` anymore, and api-key auth is never refreshed.
- **Post-login verification:** After saving credentials, `loginCommand` calls `getCurrentUser()` to verify the login succeeded (response < 400). Verification failure shows a warning but does not abort login.
- **Tag format:** Two input formats, both repeatable. `--tag TYPE:NAME` or `--tag TYPE:NAME:VERSION` accepts colon-separated tags (e.g., `--tag language:python:3.11`). `--xml-tag` accepts pre-formed XML tags (e.g., `--xml-tag '<tag type="language" name="python" version="3.11" />'`). Both can be used together. Version in `--tag` accepts MAJOR, MAJOR.MINOR, or MAJOR.MINOR.PATCH with optional pre-release suffix; `v` prefix is stripped. `--xml-tag` validates required `type` and `name` attributes, optional `version`, rejects unknown attributes, and normalizes to canonical attribute order. The dynamic tool handler in `tool-commands.js` special-cases schema properties by name: a `tags` property gets the `--tag`/`--xml-tag` pair and is serialized via `collectTags(options)` into the `tags` argument; a `sources` property gets `--sources` (`parseSources`); a `feedback` property gets repeatable `--feedback` (`parseFeedbackEntries`). These special cases are wired only when the tool's `inputSchema` declares the corresponding property, so a tool that does not accept tags (e.g., `share_feedback`) never gets those flags.
- **Output:** Default output is compact JSON via `output()`. Use `--pretty` for human-readable output with markdown rendering and ANSI formatting. Auth commands (login, logout) always use styled terminal output via banner.js. Errors go through `outputError()` which calls `process.exit(1)`.
- **OAuth client cache:** dynamically-registered client info is stored in `~/.spark/settings.json` under the `clients` key, keyed by API base URL — the provider's `clientInformation()` storage.
- **Version checking:** Three separate systems: (1) npm registry check for "update available" notifications — cached under `latestVersion` with 24-hour TTL; (2) backend compatibility check (`GET /api/cli/compatibility`) for blocking outdated CLIs and deprecation warnings — cached under `compatibility` with 4-hour TTL; (3) skills version check from GitHub raw content (`memcoai/spark-cli-skills/main/VERSION`) — cached under `skillsVersion` with 24-hour TTL. All fail open on network errors. Skills notifications include IDE-specific update commands based on stored init choices. `spark update` reuses system (1)'s `fetchLatestVersion` to tell "genuinely up to date" apart from "newer version held back by npm's install-window setting (min-release-age / before)" — in the latter case it reports the available version and the `--min-release-age=0` override instead of "already on the latest version".
- **Init persistence:** `spark init` saves IDE choices and installed skills version. Project scope writes `init` to local `.spark/settings.json` AND upserts into global `projects` array. Global scope writes `globalInit` to `~/.spark/settings.json`. Version checks read local `init` first, then fall back to `globalInit`.
- **Global-only IDEs (Codex):** IDE keys in `GLOBAL_ONLY_IDES` (`constants.js`, currently `['codex']`) install plugins that have no project/user scope. They are ALWAYS recorded in `globalInit` (merged with any existing entry) regardless of the chosen install scope — never in local `init` or the `projects` array — so a single global record governs install/removal. Consequently a project-scoped `spark disable` never tears down Codex; it is shared across projects and removed only by `spark uninstall`. `setupCodex`/`uninstallCodexPlugin` take no scope; `spark init` prints a note when Codex is selected with project scope. To keep these IDEs visible everywhere despite living only in `globalInit`, `getInitData()` merges `GLOBAL_ONLY_IDES` from `globalInit` into the local record it returns, so `spark status`/`spark update`/variant-swap all see Codex even when a project has its own local `init`. `ensureCorrectVariant` honors this by writing a swapped Codex's variant back to `globalInit` and stripping global-only IDEs from the local `init` write (so the merged view never leaks Codex into the local record).

Tests cover input parsing and validation without external service dependencies. Command tests mock `console.log` and `process.exit` to verify error output without hitting the API. The modules are written for dependency injection (a `deps` object overriding the SDK `Client`/transport, `getAuthToken`/`getAuthMode`, the SDK `auth()` orchestrator, `makeProvider`, etc.), so OUR logic can be exercised with no live server. After the Phase 2 SDK-OAuth cutover, the unit suites deliberately do NOT mock the SDK's OAuth `auth()` orchestrator or the `Client`/transport just to assert how we wire them — that real integration (login, token refresh, tool calls) is covered by a **manual `spark login` smoke test**. What stays unit-tested is OUR own logic: `SparkOAuthProvider`'s storage/redirect adapters (`test/oauth-provider.test.js`), `getAuthToken`/`getAuthMode`/`getCurrentUser` gating (`test/api.test.js`), `validateArgs` against the real SDK ajv (`test/mcp-client.test.js`), and the schema-driven flag derivation in `src/tool-commands.js` (`test/tool-commands.test.js`).
